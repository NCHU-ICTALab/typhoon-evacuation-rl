# 颱風封港前撤離排序 PoC

## 1. 目標

在預測港口將因風力達管制門檻而停止出港前，根據船舶整備時間、港口入口、航道占用、
拖船容量與風險分數，提出可解釋的撤離順序，並列出無法在截止前撤離的船舶。

本系統是決策輔助，不發布封港命令，也不取代港長、VTS、引水人或船長。

## 2. 為何選這條線

既有結果顯示一般負載下等待很低，RL 沒有穩定增益；颱風情境則天然具有：

- 明確且不可違反的安全截止時間；
- 短時間大量出港需求；
- 拖船、引水與航道容量下降；
- 撤不完哪些船比平均等待時間更重要的目標。

## 3. 非即時資料策略

| 資料 | PoC 使用方式 | 分類 |
|---|---|---|
| 高雄港 115.03 防颱作業規定與進出港管制基準 | 將颱風期間平均風力 7 級停止出港編為硬限制 | 公開、靜態規則 |
| data/ua1008l.sqlite | 唯讀抽取某一歷史日的出港申請、GT、碼頭與入口 | 本機靜態歷史樣本，不進 Git |
| NOAA IBTrACS | 後續一次性下載歷史颱風路徑，不需輪詢 | 公開歷史資料，第一版尚未接入 |
| ERA5／Copernicus wave reanalysis | 後續按事件與區域一次性下載小切片 | 公開歷史資料，第一版尚未接入 |
| 風力上升曲線 | 依 closure_hour 產生 | **合成，只供訓練／壓測** |
| 拖船容量、過航時間、整備時間壓縮 | 情境參數 | **合成，只供訓練／壓測** |
| 風險分數 | 船舶識別欄位雜湊產生危險品、吃水、機動性與主機整備 proxy | **合成、與 GT 解耦、不是官方優先序** |

PoC 不執行持續型 scraper，也不新增大型資料庫。輸出報告使用固定檔名覆寫。

## 4. 第一版架構

~~~text
既有 ua1008l.sqlite（唯讀）
          │
          ▼
build_scenario.py ── 船舶歷史模板 + 合成氣象／資源
          │
          ▼
rules.py ────────── 官方出港風力硬限制
          │
          ▼
planner.py ──────── FCFS 與 risk_aware 兩種可解釋基線
          │
          ▼
run_poc.py ──────── JSON + Markdown 比較報告
~~~

第一版先建立可驗證的規則、資料契約與基線。後續 RL 或最佳化模型必須超越這些基線，且
仍使用同一套硬限制，避免用 reward 換取不安全行為。

## 5. 決策與 KPI

每次決策必須同時滿足：船舶已完成整備、入口未關閉、入口仍有容量、拖船足夠，且預估
通過港口時間不晚於封港截止。

第一版輸出：截止前撤離艘數與 GT、風險點數、未撤離清單與原因，以及每艘船的時程。

## 6. 策略

- fcfs：依歷史申請引水時間排序。
- risk_aware：先比較安全餘裕，再比較研究用風險分數、GT 與拖船需求。

risk_aware 不是官方優先順序，而是後續 AI／最佳化模型的第一個可解釋對照組。

## 7. 執行

~~~bash
.venv/bin/python -m typhoon.run_poc --db data/ua1008l.sqlite
.venv/bin/python -m pytest tests/test_poc.py -q
~~~

預設覆寫 typhoon/out/ 下的 latest_scenario.json、latest_report.json、latest_report.md。

## 8. 誠實邊界

- ua1008l 是歷史出港事件模板，不代表颱風當下的實際滯港船舶清單。
- 第一版沒有危險品、實際吃水、主機狀態、引水班表與命名拖船。
- 風力曲線與資源容量是合成資料；可訓練策略，不能驗證真實封港成效。
- 浪高門檻在公開基準中主要限制進港；本 PoC 聚焦出港撤離，不擅自改寫成出港門檻。
- 正式系統仍需接入當次 VTS 船舶清單、港口指定海氣象儀與人工覆核。
